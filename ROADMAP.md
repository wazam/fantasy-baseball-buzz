# Roadmap

Tracks two kinds of ideas for future development: planned features actually committed to a future release, and proposed features that are just collected ideas, not actively planned or prioritized.

## Planned Features

1. **Better Player Matching**: Map nicknames to the names other sources use, such as Kike Hernandez to Enrique Hernandez, once a source sends one. Match by a shared ID where sources expose one: MLB's players trend fills `Id_MLB` by name, so a source that also sends MLB's player ID could match on it instead. Matching lives in `name_keys()` and `match_score()` in `src/db.py`, and aliases would go into `name_keys()`. No one has yet checked whether ESPN's, Fantrax's, NFBC's, or CBS's player data carries MLB's ID.

2. **Recheck Player Matching Before the Next Release**: Check the names that have caught matching out before, and merge or fix any that come out wrong: Luis Garcia, Luis Gonzalez, Josh Smith (two on one team), Luis Castillo, Diego Castillo, Will Smith, Wilmer Flores and Luis Ortiz (each a batter and a pitcher who share a name), Shohei Ohtani (one player who is both), Carlos Perez, Cristian Santana, Kevin Smith, Jose Martinez, Cristian Hernandez, Gabriel Arias, Adrian Hernandez, Moises Gomez, and Javy Guerra. Run the MLB Players trend first, so each major leaguer's row carries an MLB ID. `db.py duplicates` lists every name on more than one row, and the README's Your Data section has the `duplicates` and `merge` steps.

3. **CBS League Trends**: CBS's most rostered and started, and activated and deactivated players, exist only inside a CBS league. Read them from a public CBS league the user creates, with its URL in an optional setting such as `CBS_LEAGUE_URL`, added everywhere `FANTRAX_LEAGUE_ID` appears (`compose.yaml`, the README's compose block and settings table, and `src/sources.py`). Finding which league pages hold these lists is the first step.

4. **Yahoo Trade Market**: [Trade Market](https://baseball.fantasysports.yahoo.com/b1/playertrades) lists the last 10 trades as groups of players, with no number per player to store yet, such as how often each player was traded. Yahoo takes its fantasy pages offline between seasons, so this can only be built in season.

5. **More Sources**: Some of these are on the Index page as not yet supported, each already in `src/sources.py` with its URL and no labels. The comment at the top of `src/sources.py` has the steps for adding a source, and `src/source_mlb.py` is the shortest example. The players table already reserves an `Id_` column for several (`Id_RotoBaller`, `Id_FantasyPros`, `Id_RTSports`, `Id_FanGraphs`, `Id_RotoWire`, `Id_BaseballReference`, `Id_Razzball`), so their players can be matched by ID once a scraper exists. Fleaflicker, FB Think Tank, LineupExperts, FantasySP, RotoChamp, Pitcher List, and Closer Monkey have none yet.

6. **More Trends on Current Sources**: The trends the Index page lists as not yet supported for ESPN (12), CBS (9), and Yahoo (1), each already in `src/sources.py` with its URL and no labels. The newest are Yahoo's Draft Analysis (ADP), CBS's two-start and probable pitchers, and ESPN's depth charts. ESPN's projections, draft results, and player rater may come from the same ESPN data service the Players trend reads (`src/source_espn.py`), and Yahoo's Draft Analysis entry has a comment on finding its data.

7. **More Data Ideas**: Baseball Savant, MLB Pipeline and Baseball America prospect rankings, MiLB trending players, betting odds (Vegas Insider, BettingPros), and DFS sites (Swish Analytics, RotoGrinders). None has been looked at yet.

8. **Browser for Scrapers**: Before writing a browser scraper, check whether the page loads its table from data Buzz can read directly, as RotoWire's pages do. If a source still needs a browser, run Firefox as an optional browser service in `compose.yaml`, which Buzz drives over the network with a `SELENIUM_URL` setting, rather than inside the Buzz image. The browser then gets its own memory and process limits (about 1 GB and 512), while Buzz keeps its hardening. Firefox, geckodriver, and Selenium's local driver then come out of the image, taking it from 511 MB to about 110 MB. Inside Buzz's container today, Firefox crashes at the `pids_limit` of 128, since each of its threads counts, and loading a busy page fills the 512 MB memory limit. Bot protection such as Cloudflare's challenge stops a browser too, so it doesn't help with LineupExperts, FantasySP, or FanGraphs at times.
    - Review first: no scraper uses `src/util_webdriver.py` today, so Firefox (233 MB) and Selenium (35 MB) are in the image only for that file's self-test and the README screenshots. Decide whether to take them out of the image now, ahead of the browser service.
    - In code, `src/util_webdriver.py` would open a remote session at `SELENIUM_URL` instead of starting Firefox itself.
    - Check that the browser image runs on arm64 as well as amd64, since Buzz publishes both.
    - The README screenshots are taken with the Buzz image's Firefox today, so they'd move to the browser service too.

9. **Sources Built in the Browser**: FB Think Tank's [projections](https://www.fbthinktank.com/projections), [rankings](https://www.fbthinktank.com/rankings), [ADP](https://www.fbthinktank.com/adp), [sleepers](https://www.fbthinktank.com/sleepers), and [busts](https://www.fbthinktank.com/busts), [FanRanked's streamers](https://www.fanranked.com/streamers), [DailyWaivers' SP streaming tool](https://dailywaivers.com/tools/sp-stream), and [Stats and Matchups](https://www.statsandmatchups.com/#matchups?mode=projected_pitchers&day=Today) build their tables in the browser, so their scrapers would need item 8's browser service, if their data can't be read directly. FB Think Tank is a Wix site, FanRanked reads its data from Supabase, and DailyWaivers is a Nuxt app, so start by looking at the requests each page makes.

10. **Teams Page**: A teams table and page for numbers that belong to a team rather than a player, built like the Players page. With 30 fixed teams, there's no name matching: rows can key on the team abbreviations `standardize_team_name()` in `src/db.py` already produces. Start with park factors ([FantasyPros](https://www.fantasypros.com/mlb/park-factors.php), [hashtagbaseball](https://hashtagbaseball.com/mlb-park-factors), both plain HTML tables) and [team stats](https://www.rotowire.com/baseball/stats-team.php) (RotoWire, JSON from `tables/team-stats.php`). LineupExperts' [home and away splits](https://www.lineupexperts.com/Reports/MLB/Home-Away?flt_stattype=Batting) and [park factors](https://www.lineupexperts.com/baseball/park-factors) turn away automated requests. Per-game numbers, such as probable pitchers, matchups, [expert picks](https://www.cbssports.com/mlb/expert-picks/) (CBS), and betting odds, may need a games table of their own. Odds would come from an odds API with a key in `.env` rather than a sportsbook such as [DraftKings](https://sportsbook.draftkings.com/leagues/baseball/mlb), since sportsbooks' terms generally forbid scraping.

11. **Column Presets**: Saved sets of Players page columns, such as streaming pitchers, closers, or roster trends, to switch between with one click instead of hiding columns one at a time. The Players page keeps hidden columns in the browser's `players-prefs` (`hidden` for whole sources, `hiddenColumns` for single columns, in `templates/pages/players.html`), so a preset can be a named list of columns to show.

## Proposed Features

1. **League Roster Imports**: Import the rosters of your own leagues on ESPN, Yahoo, CBS, Fantrax, and NFBC to fill the Roster column, which the players table already has but nothing fills. For a private ESPN league, read it through ESPN's data service with `ESPN_LEAGUE_ID` and the `espn_s2` and `SWID` browser cookies. v0.4.0 dropped `ESPN_LEAGUE_ID`, so this would bring it back as an optional setting, next to the existing `FANTRAX_LEAGUE_ID`.

2. **Automated Scraping Schedules**: Queue each trend automatically on its `run_frequency` (`daily`, `weekly`, or `once`) through the background job queue in `src/jobs.py`, instead of only from its card's Run button. Buzz runs a single Gunicorn worker so the queue lives in one process (see the Dockerfile's `CMD`), so a scheduler thread there would run once. What `once` means needs deciding, such as once per season.

3. **Historical Trend Analysis**: Analyze changes in player value over time using archived JSON payloads. Every run's results stay in `data/results` as `<timestamp>_<source>-<trend>.json`, and `data/results/runs.jsonl` logs each run, so history can be rebuilt from them with `process_json_file()` in `src/db.py`, the reader `db.py import` uses.
